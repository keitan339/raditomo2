# DB設計

## 設計方針

- PostgreSQL を使用する
- 主キーはサロゲートキー（`BIGSERIAL` または `BIGINT GENERATED BY DEFAULT AS IDENTITY`）を基本とし、ラジコ由来のID（エリアID・放送局ID）はそのまま自然キーとして利用する
- タイムスタンプは `TIMESTAMP WITH TIME ZONE` を使用。アプリ全体は JST 固定だが、DBレベルでは TZ 付きで保持する
- 「動的照合」方式のため、予約レコードは生成しない。ダウンロード対象は登録 × 番組表 × 履歴の照合で都度決定する
- マイグレーションには **Flyway** を使用する

## 外部キーカスケード方針

- `users` 削除: 想定シナリオなし（個人利用かつ許可リストで管理）。論理削除（`is_active=false`）で対応
- `download_registrations` 削除: `download_histories.registration_id` は `ON DELETE SET NULL`（履歴は保持する要件のため）
- `download_histories` 削除（ユーザー操作）: `playback_positions` も `ON DELETE CASCADE`

## マイグレーション

- Flyway で `db/migration/V1__initial_schema.sql` から順次管理
- 初期データ（areas, stations のシード）は `V2__seed_master_data.sql`
- 開発中の追加変更は `V3__...`, `V4__...` と追加形式（既存ファイル改変は禁止）

## クエリ例

### 動的照合（F2: ダウンロード対象抽出）

#### タイムフリー期限の厳密判定

要件: 「放送日（5:00区切り）から7日間で、8日目の午前5時に聴取不可」

例: 4/24 5:00〜4/25 4:59 放送の番組 → 期限切れ時刻 = **5/2 5:00:00 JST**

実装は SQL 一発ではなく **Java 側で算出** する：

```java
// 期限切れ時刻 = 放送日（5:00区切り）+ 8日 5:00:00 JST
public LocalDateTime expiresAt(LocalDateTime broadcastStartAt) {
    // 放送日（5:00区切り）= broadcastStartAt が 5:00未満なら前日扱い
    LocalDate broadcastDate = broadcastStartAt.toLocalTime().isBefore(LocalTime.of(5, 0))
        ? broadcastStartAt.toLocalDate().minusDays(1)
        : broadcastStartAt.toLocalDate();
    return broadcastDate.plusDays(8).atTime(5, 0);
}

// F2 実行時
if (now.isBefore(expiresAt(broadcastStartAt))) {
    // ダウンロード対象
} else {
    // 期限切れ → EXPIRED で履歴記録、対象外
}
```

#### SQL 例（候補抽出のみ。期限内かは Java 側で再判定）

```sql
-- 一回限り登録の候補抽出
SELECT r.id AS registration_id, p.id AS program_id, p.*
FROM download_registrations r
JOIN programs p
  ON p.station_id = r.station_id
 AND p.broadcast_start_at = r.broadcast_start_at
WHERE r.registration_type = 'ONCE'
  AND r.status = 'ACTIVE'
  AND p.broadcast_end_at <= NOW()
  AND NOT EXISTS (
    SELECT 1 FROM download_histories h
    WHERE h.user_id = r.user_id
      AND h.station_id = r.station_id
      AND h.broadcast_start_at = r.broadcast_start_at
      AND h.status = 'SUCCESS'
  );

-- 毎週登録の候補抽出（手順1: 登録時刻と一致する番組）
SELECT r.id AS registration_id, p.id AS program_id, p.*
FROM download_registrations r
JOIN programs p
  ON p.station_id = r.station_id
 AND p.day_of_week = r.day_of_week
 AND p.title = r.title
WHERE r.registration_type = 'WEEKLY'
  AND r.status = 'ACTIVE'
  AND p.broadcast_end_at <= NOW()
  AND NOT EXISTS (
    SELECT 1 FROM download_histories h
    WHERE h.user_id = r.user_id
      AND h.station_id = r.station_id
      AND h.broadcast_start_at = p.broadcast_start_at
      AND h.status = 'SUCCESS'
  );
```

※ 毎週マッチングの「手順1〜4」は Java 側でロジック分岐する（SQL一発では複雑になるため）。

### 毎週マッチング手順4（番組名不一致時の挙動）

要件 F2 の手順4「番組名が見つからない場合は登録時刻でDLし、DB上の該当時間帯の番組名で保存」について、別番組（特番・差替え）が放送されていても **そのままダウンロード対象とする**。

**意図**: 番組終了・差替え・特番への切替などをユーザーが気付きやすくするため。新しい番組名で履歴に残ることで「もしかしたらこの後も継続して聴きたい番組かも」とユーザーが判断できる。スキップせず必ずダウンロードする方針。
